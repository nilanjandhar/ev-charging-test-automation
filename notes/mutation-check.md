# Mutation check — evidence that the suite catches real bugs

Generated by `python tools/mutation_check.py`. Reproduce it yourself; the output
below is a paste of one run, not a claim.

Each mutant is applied to a **scratch copy** of `service/` — the real service is
never modified — and the merge-gate layers are run against the mutated copy
(`pytest -m 'not e2e and not perf and not ui and not slow'`). Gate layers only:
a mutant caught solely by a nightly job is a mutant that reaches main.

The last entry is a deliberate **no-op control**. It changes nothing, so it must
SURVIVE. If the harness ever reported it as killed, the harness would be broken and
every result above it worthless.

## Where the net is thin

Two mutants are killed by very few tests, and that is the honest read of this run:

- `recency-inverted` (`ORDER BY timestamp DESC` -> `ASC`) — 3 tests, all in
  `test_recency_semantics.py`. This is the most damaging realistic bug in the
  service and the net under it is narrow.
- `metrics-errors-over-all-history` — **1 test**. If someone deleted
  `test_metrics_aggregate_only_the_latest_report_per_station`, superseded reports
  could leak into the network error total with nothing to stop them.

Both are named as gaps in `TEST_STRATEGY.md`.
